## Stop finding: VM-028

A failed grocery regeneration deletes saved generated groceries. This meets the user's explicit data-loss stop condition and the existing ledger's P0 definition. No production exposure is asserted; this was reproduced using only synthetic emulator data.

Exact Chrome steps at http://127.0.0.1:5173:

1. Sign in as the requested synthetic test account. Settings contain onboardingCompleted=true and measurementUnit=imperial. All services use demo-viomacro; Auth 9099, Firestore 8085, Storage 9199. Functions was not started and AI environment switches remained unset.
2. Seed Audit Chicken Rice: four servings, 24 oz chicken, 2 cups rice, legacy 2-3 cloves garlic, eggplant and black pepper. Save lunch Monday-Friday in the week starting 2026-10-19.
3. Add to List creates five generated grocery documents. Keep the separate Manual control item. Mark Chicken breast purchased. Read Firestore: five generated + one manual; chicken isChecked=true.
4. In Meal Planner choose Next week (Oct 26), Create New Plan, Open Plan Wizard, Start from Scratch (Empty Grid).
5. Click Add to List without confirming/saving that empty draft.
6. The app reports **No recipes in plan**. Firestore now contains only Manual control item. All five generated documents, including checked chicken, are gone.
7. Navigate to Grocery and reload. Only the manual item remains, although the saved current-week meal plan still exists.

No failure hook was used. A DOMStorage hook attempt was rejected as unsupported before setting anything; the successful reproduction used ordinary UI only.

Evidence in `_local/qa/bug-hunt-2026-10-22/`:
- `groceries-before-failure.json` and `groceries-after-empty-plan.json`: authenticated Firestore SDK reads.
- `grocery-before-failure.jpg`, `grocery-empty-plan-error.jpg`, `grocery-after-loss.jpg`.
- `grocery-empty-plan-error.txt`, `grocery-after-loss.txt`, `browser-console.json`.
- Fixture and readback scripts/data remain ignored alongside the evidence.

Root: `src/features/groceries/shopping-generator.ts:52` clears generated items before checking IDs at 64, reading recipes at 71 or completing replacement writes at 160-163. `shoppingService.ts:138-155` selects every generated item when mealPlanId is omitted, and 110-116 commits deletion batches. `MealPlanner.tsx:874` refreshes client groceries only after success, so stale UI can hide deletion until reload.

Related isolated actual-source probes also lose the generated item when recipe reads fail. Sequential delete batches and independent Promise.all replacement writes leave additional partial-failure windows. This is a separate persistence root cause, not a quantity-formatting issue. Proposed repair: validate/build the replacement first, then commit a bounded atomic replacement or equivalent preservation mechanism; define week scope explicitly. Required regressions: empty/no-ID/missing recipe, rejected read, rejected replacement, existing checked and manual items, cross-week behavior, and reload. Await Sara before implementation.
